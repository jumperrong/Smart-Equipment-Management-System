SEMS 生产管理全流程教程

从导入新产品到生产完工 · 端到端实战指南 · 以半导体光刻工艺为例

示例场景

新品 WX-100 6寸晶圆 投产，需要经历 清洗 → 光刻 → 刻蚀 → 检测 四道工序，最终在 ASML-1400 光刻机等设备上完成 100 片的生产任务。

一、整体流程概览

1. 创建产品 → 2. 表单模板 → 3. 工段库 → 4. 工序路由(生效) → 5. 生产订单(下发) → 6. 派工 → 7. 开工 → 8. 报工 → 9. 完工结案
核心依赖链： 产品 → 工序路由(必须 EFFECTIVE) → 生产订单(必须 RELEASED) → 派工(必须 RUNNING/COMPLETED) → 报工

二、创建产品（新品导入）

1产品主数据维护

导航： 当前系统暂无独立 UI 入口，通过 POST /api/v1/products 创建
所需权限： production.product_write
角色： admin / process_engineer

关键字段

  • codeString(64)产品编号（唯一），如 WX-100
  • nameString(128)产品名称，如 6寸晶圆
  • specString(255)规格型号
  • unitString(32)单位，默认"片"
  • target_cycleFloat理论节拍（秒/件），用于 OEE 计算
  • is_activeBoolean启用状态

API 调用示例

# 1. 登录获取 token（admin / Admin@1234）
curl -X POST http://localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"Admin@1234"}'

# 返回: {"access_token":"eyJ...","refresh_token":"..."}
# 将 token 写入变量 TOKEN

# 2. 创建产品 WX-100 6寸晶圆
curl -X POST http://localhost:8000/api/v1/products \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "code": "WX-100",
    "name": "6寸晶圆",
    "spec": "6inch N型 (100)",
    "unit": "片",
    "target_cycle": 30,
    "remark": "新品导入，光刻工艺验证",
    "is_active": true
  }'

# 返回示例: {"id":11,"code":"WX-100","name":"6寸晶圆",...}
# 记下返回的 product_id=11
验收： 调用 GET /api/v1/products?active_only=true 能查到 WX-100；后续在工序路由、生产订单页面的产品下拉框中能看到该产品。

三、创建表单模板（工艺数据采集字段）

2定义工艺参数采集模板

导航： 工艺文控 → 表单模板管理（路由 /form-templates）
所需权限： form_template.manage
角色： admin

表单模板定义了"派工时自动生成哪些字段需要填写"，例如光刻工序需采集：曝光能量、焦距、显影时间等。

关键字段

  • nameString模板名称，如"光刻工艺参数记录表"
  • codeString唯一编码，如 FT-LITH-001
  • categoryStringrecord(作业记录类) / guide(通用表单类)
  • field_schemaJSON字段定义数组（见下）
  • is_activeBoolean启用状态

field_schema 字段定义格式

{
  "key": "exposure_energy",        # 唯一 key（英文+下划线）
  "type": "number",                # text/textarea/number/select/radio/date/datetime/time/boolean
  "label": "曝光能量(mJ/cm²)",      # 显示名
  "required": true,
  "placeholder": "例 100",
  "unit": "mJ/cm²",
  "min": 50, "max": 200,
  "seq": 1                          # 显示顺序
}

UI 操作（推荐）

  1. 进入「工艺文控 → 表单模板管理」
  2. 点击「新增模板」
  3. 填写名称/编码，类别选 record
  4. 在可视化字段编辑器中添加字段：
    • exposure_energy (number, 必填, 范围 50-200)
    • focus_offset (number, 焦距偏移 μm)
    • develop_time (number, 显影时间 秒)
    • remark (textarea, 备注)
  5. 保存模板，记下模板 ID（如 template_id=5）

API 调用示例

curl -X POST http://localhost:8000/api/v1/form-templates \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "光刻工艺参数记录表",
    "code": "FT-LITH-001",
    "category": "record",
    "description": "光刻工序关键参数采集",
    "is_active": true,
    "field_schema": [
      {"key":"exposure_energy","type":"number","label":"曝光能量(mJ/cm²)","required":true,"unit":"mJ/cm²","min":50,"max":200,"seq":1},
      {"key":"focus_offset","type":"number","label":"焦距偏移(μm)","required":true,"unit":"μm","seq":2},
      {"key":"develop_time","type":"number","label":"显影时间(秒)","required":true,"unit":"秒","seq":3},
      {"key":"remark","type":"textarea","label":"备注","required":false,"seq":4}
    ]
  }'
验收： 模板列表可见；记下 template_id 供下一步工段引用。

四、创建工段库（可复用工艺单元）

3定义工段（绑定数据采集模板）

导航： 生产管理 → 工段库（路由 /process-sections）
所需权限： production.section_write
角色： admin / process_engineer

工段是"产品在某设备做某工艺时需要采集哪些数据"的模板化封装。一个工段可被多个产品的工序路由引用。

关键字段

  • nameString工段名称，如"光刻工序"
  • codeString唯一编码，如 PS-LITH
  • equipment_groupString允许的设备组，如 LITH_GROUP
  • form_template_idFK关联上一步的表单模板
  • standard_cycle_minFloat标准工时（分钟）
  • theoretical_uphFloat理论每小时产出
  • acceptance_criteriaText判定标准，如 CD 偏差 ±5nm

为本场景创建 4 个工段

# 工段 1: 清洗工序
curl -X POST http://localhost:8000/api/v1/process-sections \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"清洗工序","code":"PS-CLEAN","equipment_group":"CLEAN_GROUP","standard_cycle_min":15,"theoretical_uph":200,"description":"晶圆预清洗","is_active":true}'

# 工段 2: 光刻工序（绑定 FT-LITH-001 模板）
curl -X POST http://localhost:8000/api/v1/process-sections \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{
    "name":"光刻工序","code":"PS-LITH","equipment_group":"LITH_GROUP",
    "form_template_id":5,
    "standard_cycle_min":30,"theoretical_uph":120,
    "acceptance_criteria":"CD 偏差 ±5nm，套刻精度 ≤0.2μm",
    "description":"光刻曝光+显影","is_active":true
  }'

# 工段 3: 刻蚀工序
curl -X POST http://localhost:8000/api/v1/process-sections \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"刻蚀工序","code":"PS-ETCH","equipment_group":"ETCH_GROUP","standard_cycle_min":45,"theoretical_uph":80,"description":"干法刻蚀","is_active":true}'

# 工段 4: 检测工序
curl -X POST http://localhost:8000/api/v1/process-sections \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"检测工序","code":"PS-INSPECT","equipment_group":"INSPECT_GROUP","standard_cycle_min":10,"theoretical_uph":300,"description":"CD/套刻检测","is_active":true}'
验收： 工段库列表可见 4 个工段；记下各工段 ID（如 清洗=10、光刻=11、刻蚀=12、检测=13）。

五、创建工序路由并生效

4为产品定义工艺路线

导航： 生产管理 → 工序路由（路由 /routings）
所需权限： production.routing_write
角色： admin / process_engineer

路由定义了产品经过哪些工序、顺序如何、各工序引用哪个工段。创建后默认为 DRAFT，必须 生效(EFFECTIVE) 后才能被生产订单引用。

状态机

DRAFT 草稿 → release → EFFECTIVE 已生效 → (新版生效自动) → OBSOLETE 已作废

创建路由（含 4 道工序）

# 产品 product_id=11，4 道工序顺序 10/20/30/40
curl -X POST http://localhost:8000/api/v1/routings \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{
    "product_id": 11,
    "version": "v1.0",
    "remark": "WX-100 初版工艺路线",
    "steps": [
      {"seq":10,"step_name":"清洗","process_section_id":10,"standard_cycle_min":15,"equipment_group":"CLEAN_GROUP"},
      {"seq":20,"step_name":"光刻","process_section_id":11,"standard_cycle_min":30,"equipment_group":"LITH_GROUP"},
      {"seq":30,"step_name":"刻蚀","process_section_id":12,"standard_cycle_min":45,"equipment_group":"ETCH_GROUP"},
      {"seq":40,"step_name":"检测","process_section_id":13,"standard_cycle_min":10,"equipment_group":"INSPECT_GROUP"}
    ]
  }'

# 返回 routing_id，例如 5

# 让路由生效（DRAFT → EFFECTIVE）
curl -X POST http://localhost:8000/api/v1/routings/5/release \
  -H "Authorization: Bearer $TOKEN"
关键约束：
  • 生产订单创建时引用的 routing 必须 EFFECTIVE，否则报错
  • 生效后不可再编辑/删除
  • 同产品同时只能有一个 EFFECTIVE 版本，新版本生效自动作废旧版
验收： 路由列表中 v1.0 状态为「已生效」；行点击可查看 4 道工序详情。

六、创建生产订单并下发

5下达生产计划

导航： 生产管理 → 生产订单（路由 /production-orders）
所需权限： production.mo_manage
角色： admin / production_manager

状态机

DRAFT 草稿 → RELEASED 已下发 → IN_PROGRESS 执行中 → COMPLETED 已完工 → CLOSED 已结案

关键字段

  • product_idFK产品（WX-100 → 11）
  • routing_idFK工序路由（必须 EFFECTIVE）
  • batch_noString批次号，如 B20260819-01
  • plan_qtyInteger计划数量，如 100
  • priorityStringHIGH/NORMAL/LOW
  • planned_start/endDateTime计划起止时间

创建订单

# 1. 创建 MO（默认 DRAFT）
curl -X POST http://localhost:8000/api/v1/production-orders \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{
    "product_id": 11,
    "routing_id": 5,
    "batch_no": "B20260819-01",
    "priority": "HIGH",
    "plan_qty": 100,
    "planned_start": "2026-08-19T08:00:00",
    "planned_end": "2026-08-19T20:00:00"
  }'

# 返回示例: {"id":7,"mo_no":"MO-20260819-0007","status":"DRAFT",...}

# 2. 下发（DRAFT → RELEASED）
curl -X PUT http://localhost:8000/api/v1/production-orders/7 \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"status":"RELEASED"}'
关键约束：
  • 草稿状态（DRAFT）不能派工，必须先「下发」
  • routing_id 必须指向 EFFECTIVE 路由
  • mo_no 自动生成：MO-YYYYMMDD-NNNN
验收： 订单列表中可见 MO-20260819-0007，状态「已下发」；行点击可查看订单详情抽屉。

七、派工到设备与作业员

6为每道工序创建派工单

导航： 生产管理 → 派工管理（路由 /dispatches）
所需权限： production.dispatch_assign
角色： admin / production_manager / team_leader

派工是连接"计划"与"执行"的桥梁。每个派工对应 MO 的一道工序，可指定具体设备和作业员。派工创建时会自动按工段关联的表单模板初始化一份空白工艺数据表单。

关键字段

  • mo_idFK生产订单（必须非 DRAFT）
  • step_seq / step_nameInt/String工序序号/名称（与路由步骤对应）
  • equipment_idFK派到哪台设备
  • assigned_operator_idFK作业员
  • dispatch_qtyInteger派工数量
  • process_section_idFK引用工段（自动解析表单模板）

状态机

QUEUED 排队 → ASSIGNED 已分配 → RUNNING 执行中 → COMPLETED 已完工

为 4 道工序分别派工

# 派工 1: 清洗工序 (序号 10)，派到 DNS-3000 清洗机
curl -X POST http://localhost:8000/api/v1/dispatches \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{
    "mo_id": 7, "step_seq": 10, "step_name": "清洗",
    "process_section_id": 10,
    "equipment_id": 4,
    "assigned_operator_id": 8,
    "dispatch_qty": 100
  }'

# 派工 2: 光刻工序 (序号 20)，派到 ASML-1400 光刻机
curl -X POST http://localhost:8000/api/v1/dispatches \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{
    "mo_id": 7, "step_seq": 20, "step_name": "光刻",
    "process_section_id": 11,
    "equipment_id": 2,
    "assigned_operator_id": 8,
    "dispatch_qty": 100
  }'

# 派工 3/4 类似，分别派到刻蚀机、检测设备
# 系统会自动为每个派工创建空白 FormRecord（按工段绑定的模板）
自动行为：
  • 派工时按工段 form_template_id 自动初始化一份草稿 FormRecord
  • 表单标题自动生成：派工#{id} · {工序名} · {模板名}
  • 模板停用时不阻断派工，仅跳过初始化
验收： 派工列表可见 4 条派工记录，状态「已排队」；行点击可查看派工详情抽屉；点击 MO 号可跳转订单详情。

八、派工开工

7将派工转为执行中

导航： 生产管理 → 派工管理 → 操作列「开工」按钮
所需权限： production.dispatch_assign

开工将派工从 ASSIGNED → RUNNING，同时自动将所属 MO 从 RELEASED 联动为 IN_PROGRESS。

UI 操作

  1. 进入派工管理页面
  2. 找到状态为「已分配」的派工行
  3. 点击操作列的「开工」按钮
  4. 确认弹窗后，状态变为「执行中」

API 调用

# 派工 QUEUED → ASSIGNED（分配设备和作业员后）
curl -X PUT http://localhost:8000/api/v1/dispatches/{dispatch_id} \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"status":"ASSIGNED","equipment_id":2,"assigned_operator_id":8}'

# 派工 ASSIGNED → RUNNING（开工）
curl -X PUT http://localhost:8000/api/v1/dispatches/{dispatch_id} \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"status":"RUNNING"}'
自动副作用：
  • 派工自动写入 actual_start（实际开始时间）
  • 若 MO 为 RELEASED，自动联动转为 IN_PROGRESS 并写 MO.actual_start
  • RUNNING 状态下可「暂停」(HELD) 或「完工」(COMPLETED)
暂停与恢复： 设备 DOWN 机时系统自动将所有 RUNNING 派工转为 HELD 并关联维修工单；恢复后可继续 RUNNING。

九、报工（合格/不良/工时）

8逐工序提交报工记录

导航： 生产管理 → 报工记录（路由 /labor-reports）
所需权限： production.labor_report（报工）、production.labor_correct（修正/删除）
角色： admin / team_leader / operator

报工是生产执行的最终数据采集点。一次派工可多次报工（累加），每次报工自动联动更新派工和 MO 的数量，当完工+报废达到计划量时 MO 自动转为 COMPLETED。

关键字段

  • dispatch_idFK派工单（必须 RUNNING/COMPLETED）
  • input_qtyInteger本次投入数量
  • good_qtyInteger合格数量
  • defect_qtyInteger不良数量
  • session_start/endDateTime作业时段起止
  • man_hoursFloat人×小时
  • defect_detailJSON按缺陷码分拆，如 {"划伤":2,"异物":1}

报工示例（光刻工序完成 100 片，95 合格 5 不良）

# 报工（一次报 100 片）
curl -X POST http://localhost:8000/api/v1/labor-reports \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{
    "dispatch_id": 18,
    "session_start": "2026-08-19T10:00:00",
    "session_end": "2026-08-19T14:00:00",
    "input_qty": 100,
    "good_qty": 95,
    "defect_qty": 5,
    "defect_detail": {"划伤":2,"异物":2,"颗粒":1},
    "man_hours": 4.0,
    "remark": "光刻完成，5 片不良已隔离"
  }'
报工联动逻辑：
  1. 派工 completed_qty += good_qty（95）
  2. 派工 scrapped_qty += defect_qty（5）
  3. 派工 wip_qty = max(0, dispatch_qty - completed - scrapped)
  4. MO 同步累加 completed_qty / scrapped_qty / input_qty
  5. 若 completed_qty + scrapped_qty ≥ plan_qty 且 MO 为 IN_PROGRESS，自动转 COMPLETED 并写 actual_end
  6. 自动创建 ProductionRecord（编号 LR-000001），用于 OEE 看板分析

UI 操作

  1. 进入报工记录页面
  2. 点击「新增报工」
  3. 选择派工单（下拉显示 #id 工序号 工序名）
  4. 填写作业起止时间、投入/合格/不良数量、人时
  5. 点击「提交」，系统弹窗显示摘要确认
  6. 确认后报工记录创建，派工和 MO 数量自动更新
验收： 报工列表可见记录；行点击可查看报工详情抽屉；点击派工号可跳转派工详情。

十、完工与结案

9MO 完工与结案闭环

导航： 生产管理 → 生产订单
所需权限： production.mo_manage

完工阶段

当所有工序报工完成、MO 的 completed_qty + scrapped_qty ≥ plan_qty 时，系统自动将 MO 从 IN_PROGRESS 转为 COMPLETED 并写入 actual_end。

也可手动触发：

curl -X PUT http://localhost:8000/api/v1/production-orders/7 \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"status":"COMPLETED"}'

结案阶段

完工后的 MO 进入待结案状态，由生产经理执行结案（COMPLETED → CLOSED），写入 closed_by。

curl -X PUT http://localhost:8000/api/v1/production-orders/7 \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"status":"CLOSED"}'
结案后状态：
  • MO 状态变为「已结案」
  • 所有派工应为 COMPLETED 状态
  • 报工记录已锁定，不可再修正
  • 关联的 FormRecord 已审核归档
  • 生产数据已进入 OEE 看板统计

十一、流程总结与状态机速查

端到端状态流转图

阶段 对象 初始状态 过程状态 终态
1. 产品 Product is_active=true - is_active=true
2. 模板 FormTemplate is_active=true - is_active=true
3. 工段 ProcessSection is_active=true - is_active=true
4. 路由 Routing DRAFT release → EFFECTIVE EFFECTIVE
5. 订单 ProductionOrder DRAFT RELEASED → IN_PROGRESS → COMPLETED CLOSED
6. 派工 Dispatch QUEUED ASSIGNED → RUNNING → COMPLETED COMPLETED
7. 报工 LaborReport 创建即终态 累加联动派工/MO 数量 触发 MO 自动 COMPLETED

关键自动联动一览

触发动作 自动副作用
派工开工 (ASSIGNED→RUNNING) 写 actual_start；若 MO=RELEASED 自动转 IN_PROGRESS 并写 MO.actual_start
派工完工 (RUNNING→COMPLETED) 写 actual_end
报工创建 派工/MO 数量累加；满量自动 MO→COMPLETED；自动创建 ProductionRecord 入 OEE
路由生效 (DRAFT→EFFECTIVE) 写 effective_date、next_review_date(+1年)；同产品旧 EFFECTIVE 自动转 OBSOLETE
设备 DOWN 机 该设备所有 RUNNING 派工自动转 HELD 并关联维修工单

核心约束总结：
  1. 产品 → 路由 → 订单 → 派工 → 报工，必须按序创建
  2. 路由必须 EFFECTIVE 才能被 MO 引用
  3. MO 必须 RELEASED 才能派工
  4. 派工必须 RUNNING/COMPLETED 才能报工
  5. 报工满量自动触发 MO 完工
